# 本地闭环与端侧决策引擎：Jev 心法 × 我们的架构

> 技术沉淀 · 2026-10-10 · 设计文档（未实现）
> 参考对象：Jev（TypeSafe System One）、Kev（jaredpalmer/kev）、Laya（NandhaKishorM/laya）——
> **只借鉴判别式决策的心法，不引入任何新模型**。结论来自调研：Laya 803MB safetensors（PyTorch 非自回归）、
> Kev 是 Qwen3.5-0.8B 基座 + LoRA + head（合计 ~1.6GB，纯 PyTorch 栈）、Jev 官方仅托管 API——
> 三者都无法跑进手机，但它们的**协议**（Choice / Score / Noul + 校准概率）是可以在我们已有架构上实现的。

## 0. 赛道定位：端侧 UI 决策引擎（叙事判断，非技术结论）

> ⚠️ 本章是方向性判断，不是已验证的结论。下面的对比表里，我们的延迟/离线/吞吐都还没有实测数据；
> 唯一的硬事实是：FastPicker 精确层 1-2ms、语义层 ~93ms、Framer 帧差 p50 ~55ms 已实测（见第 6 章）。
> 其余（飞轮、决策头、离线能力）都是推演，等阶段 A 跑出数据后再回来修订本章。

**一句话**：让手机自己"知道下一步点什么"——不是云端遥控，是端侧一个会自我进化的极小判别引擎。

**对标格局**：

| 方案 | 理解在哪 | 每步延迟 | 离线 | 会进化 |
|---|---|---|---|---|
| 努比亚豆包 | 云端多模态 | 0.3-1s（链路快但仍有往返） | ❌ | ❌ |
| Jev / Kev / Laya | 本地通用判别模型 | 33-500ms | ✅ | ❌（通用，非 UI 特化） |
| Appium / 脚本宏 | 人工写死规则 | ~0ms | ✅ | ❌ |
| **我们** | **本地 UI 特化判别 + 云端兜底** | **0.1-0.5s** | **✅** | **✅ 数据飞轮** |

**为什么是"新赛道"而不是"抄 Jev"**：Jev 类模型追求"通用决策"（合同、客服、路由……什么都能判），所以最小也要 803MB-1.6GB，且没有 UI 场景的专属信号（角色、层级、可点击性、帧差）。我们把决策面**收窄到"UI 自动化"这一个专业**，就能做到 15MB 级（bge 已有）+ 毫秒级判别头，并且**唯一拥有"云端纠错 → 本地蒸馏 → 越用越准"的数据飞轮**——这是别人想抄也抄不走的（需要完整的云端+本地+执行闭环才有数据）。

## 1. 为什么抄心法而不是抄模型

Jev 的本质不是"某个模型"，是三个设计决策：

| Jev 心法 | 含义 | 我们的对应物 | 状态 |
|---|---|---|---|
| **判别式，不生成** | 单次前向直接给结论，不做自回归生成 | FastPicker 精确层（1-2ms）/ bge 语义层（~93ms） | ✅ 已有 |
| **Noul（无把握即弃）** | 置信度不足时输出"不知道"，而非硬猜 | bge 余弦阈值 0.62，低于即升级云端 | ✅ 已有 |
| **类型化输出** | Choice（选一个）/ Score（打分）/ Noul（放弃），三态分离 | 候选选择 / 可加多候选打分 / 升级路径 | ⚠️ 可延伸 |

**结论**：本地闭环不缺模型，缺的是**把"理解"变成可判别的东西**。

## 2. 核心架构：云端预编译决策程序

```
┌─────────────────────────── 云端（3-4s，多模态，只跑一次） ───────────────────────────┐
│  任务: "打开设置，关闭WiFi"                                                           │
│  ↓ 理解（多模态看屏幕 + 目标分解）                                                     │
│  ↓ 编译（输出结构化决策程序，一次下发）                                                 │
│  Plan[step1: 找"设置"→点 → 验证出现WiFi入口                                            │
│        step2: 找"WiFi"→点 → 验证开关出现                                                │
│        step3: 找开关→点 → 帧差验证页面变化]                                             │
└──────────────────────────────────────────────────────────────────────────────────────┘
                                    ↓ 一次编译，N 次本地执行
┌─────────────────────────── 本地闭环（每步 0.1-0.5s，无云端往返） ─────────────────────┐
│  循环:  PICK → ACT → VERIFY → 成功? → 下一步 / 失败 → RETRY(判别式) → 耗尽 → ESCALATE  │
└──────────────────────────────────────────────────────────────────────────────────────┘
```

**关键洞察**：努比亚豆包"每步零延迟"的本质不是本地模型够聪明，而是**云端把理解前置成了可判别的规则，本地只剩判别+执行+验证**。Jev 的"判别式"思想在本地闭环里的角色就是：每一步的决策被降维成"选 A/B/C/D 或放弃"——这恰好是 FastPicker 已经擅长的事。

## 3. 决策程序 DSL（云端编译产物）

```json
{
  "goal": "关闭WiFi",
  "escalateAfter": 3,
  "steps": [
    {
      "id": "open_settings",
      "action": {"type": "tap"},
      "target": {
        "text": ["设置", "Settings"],
        "semantic": "系统设置入口",
        "fallback": {"role": "tab", "index": 3}
      },
      "verify": {
        "anyText": ["WiFi", "无线网络"],
        "timeoutSec": 3
      },
      "onFail": {"retry": 2, "then": "escalate"}
    },
    {
      "id": "toggle_wifi",
      "action": {"type": "tap"},
      "target": {
        "text": ["WiFi", "无线网络"],
        "semantic": "wifi 开关设置页"
      },
      "verify": {
        "frameDiff": true,
        "timeoutSec": 2
      },
      "onFail": {"retry": 2, "then": "branch: find_switch"}
    }
  ]
}
```

**target 是核心**：`text`（精确/子串，走 FastPicker 第一层，1-2ms）→ `semantic`（语义锚点，走 bge 第二层，~93ms）→ `fallback`（结构兜底：角色+序号/图标）。**三层锚点按序退化**，全部失败才升级——这正是 Jev "Noul 即弃"的工程化。

## 4. 闭环状态机与判别式回溯

```
        ┌──────────────────────────────────────────────┐
        │                                              │
        ▼                                              │
    PICK ──失败──► 换下一层锚点（text→semantic→fallback）│
        │           全部耗尽 ──► ESCALATE               │
        ▼                                              │
    ACT（动作原语：tap/长按/连点/滑动）                    │
        │ 执行失败（Framer 无变化）                       │
        ▼  ──► 换动作原语（tap→长按→连点）→ 重试           │
    VERIFY ──成功──► 下一步                              │
        │ 失败（超时/帧无变化/文本未出现）                 │
        └──► RETRY（retry 计数）──耗尽──► ESCALATE      │
              （同一思路连续失败 2 次即换方向）             │
                                                       │
    ESCALATE: 携带失败证据回云端重新编译 ─────────────────┘
```

**Jev 式失败分类**（不猜原因，按可判别的证据分流）：

| 失败类型 | 判别依据 | 本地处置 |
|---|---|---|
| 选择失败 | pick 层耗尽 / 最高分 < 阈值 | 换锚点 → 换语义表述 → 升级 |
| 执行失败 | pick 成功但 Framer 帧差 ratio < 阈值 | 换动作原语 → 重试 → 升级 |
| 验证超时 | 目标文本未出现且帧无变化 | 重试 → 升级 |

**升级协议**（每次升级都比上次聪明）：ESCAPE 时携带 `{步骤id, 已尝试锚点, pick分数, 帧差数据, 动作历史}`，云端据此重新编译决策程序——不是简单重试，是带着本地证据的再规划。

## 5. Score 层：关键动作的置信度校准（可选延伸）

Jev 的 Score 输出（对候选打分）借鉴到我们的语义层：

- **双次独立匹配**：关键动作（支付、删除等不可逆操作）对同一锚点做 2 次独立嵌入匹配，两次一致且都过阈值才执行——把 bge 的偶发歧义（如"设置"撞上"设备设置"）降下来
- **多候选排序**：语义层不只取 argmax，返回 Top-3 + 分数差；分数差 < 0.05 视为"难分"，走 Noul 升级——避免在模棱两可的节点上硬猜
- 这两项都**不加新模型**，只改 FastPicker 的返回结构与调用方

## 6. 性能预算（闭环内每步）

| 环节 | 耗时 | 说明 |
|---|---|---|
| PICK 精确层 | 1-2ms | 文本匹配，绝大多数步骤止步于此 |
| PICK 语义层 | ~93ms | 仅精确层未命中时 |
| ACT 执行 | 50-200ms | 无障碍手势注入 |
| VERIFY 文本 | ~50ms | 节点树查询 |
| VERIFY 帧差 | ~55ms（p50，实测） | 动态视觉场景，见 COMPLEX_SCENARIOS.md 7.5 节 |
| **单步合计** | **0.1-0.5s** | 无云端往返，对比云端路径 3-4s |

## 7. 决策头 v2：UI 特化判别模型（推演，未验证）

> ⚠️ 本章是推演：数据从哪来、训出来能不能真的比余弦准、收益多大，**全都没有证据**。
> 在阶段 A 拿到真实升级日志之前，不投入实现。放在这里只是记录想法，避免当成方案去做。

现在的语义层（bge 余弦）就是 **v1 判别头**：它只会比文本相似度，是"通用嵌入的朴素用法"。v2 设想把它升级成**专为 UI 决策训练的判别头**，依然 15MB 级、不加新模型基座：

**输入**（一次前向，全部本地）：
```
目标描述（云端/用户给的"找设置"）─► bge 编码 ─┐
                                               ├─► 拼接 ─► 小 MLP 判别头 ─► 每个候选 score + noul 概率
候选节点（文本 + 角色 + 层级 + 可点击性）─► bge 编码 ┘        （几万参数，<1MB，<5ms）
```

**比纯余弦强在哪**：能学到**组合特征**——"设置"出现在 Tab 栏 vs 列表项 vs 开关行，语义相同但**该不该点**不同；可点击容器（文本"-"）的候选应被降权；层级浅的优先。这些都是文本相似度给不了、只能从 (目标, 屏幕候选, 正确答案) 三元组里学出来的。

**训练数据来源**：就是飞轮本身——云端升级日志里的正确答案（见第 8 章）。零标注成本。

## 8. 进化飞轮（2026-10-11 已实证首环：场景记忆）

> 原为推演章节；2026-10-11 实现并实测了**最小可用形态——场景记忆**（不做模型训练，
> 只做"记住决策 + 相似场景复用"），下面 8.1 是实测结果，8.2 起的模型蒸馏部分仍为推演。

### 8.1 场景记忆（已实现，`scripts/probes/memory.py`）

**机制**（用户洞察的工程化："每一次操作和纠正都在增加样本数据"）：
1. 每轮云端规划 → 本地执行 → **成功则存 (场景指纹, 目标, 成功决策)**；云端纠正本地错误
   时产生的"正确答案"天然成为标注
2. 下次遇到**相似场景**（屏幕文本集合 Jaccard 相似度 ≥ 0.7）→ **直接复用记忆决策，
   跳过云端**（云端 0.6-1.6s/次 → 查表 <1ms）
3. 复用后失败 → misses+1，超阈值淘汰（防错记忆固化）；同场景同目标再次成功 → 更新

**实测**（"在设置里找到深色主题并开启"，同任务跑 2 次）：

| | 轮数 | 云端调用 | 记忆命中 | 结果 |
|---|---|---|---|---|
| 第 1 次（冷启动） | 3 | **3 次** | 0 | ✅ 9.5s |
| 第 2 次（有记忆） | 4 | **2 次** | **2 次** | ✅ 9.2s |

**实测发现的陷阱（已修）**：动作改变的状态若**不在屏幕文本里**（开关的 checked 状态
dump 不输出），点击后场景指纹不变 → 记忆反复命中同一动作 → **反复点开关（开了又关）**。
修复：同一任务内相同（指纹,动作）只执行一次，重复出现视为"记忆在当前状态不适用"，
交回云端判断。

**诚实边界**：命中率受"场景序列差异"影响（起始状态/执行路径不同 → 场景不同 → 不命中）；
"死记"能覆盖重复场景（固定流程几轮后云端调用趋近于零），**泛化**（举一反三）需要下一环。

### 8.1b 下沉到 App（v1.2.125，产品级能力）

`SceneMemory.kt`（端侧实现）+ `/loop/run` 的 `useMemory` 参数 + `/memory/*` 端点组
（list/lookup/store/clear/stats）。调用方只需：

```json
{"goal": "开启深色主题", "useMemory": true, "steps": [...云端规划...]}
```

执行器自动：读屏 → 指纹 → 查记忆（命中则**忽略 steps、用记忆的决策**）→ 执行 →
成功存记忆 / 复用失败计数淘汰。报告里带 `"memory":{"hit":true,"similarity":1.0,...}`。

**实测（2026-10-11，模拟器）**：
- 第 1 次（带计划）：`memory={"hit":false,"result":"stored"}` → 云端计划执行成功并存入
- 第 2 次（**不带计划**，只有 goal + useMemory）：`memory={"hit":true,"similarity":1.0,
  "result":"hit-confirmed"}` → **记忆命中并执行成功** —— 云端完全不参与 ✓
- `/memory/stats`：记忆条目 1 条、累计命中复用 1 次

**意义**：云端调用方对重复场景可以**连 steps 都不给**（省掉规划 + 传输）；记忆库同时是
判别头训练的现成标注数据集（场景 + 目标 + 成功决策）。

### 8.1c checked 标记（v1.2.126）—— 一举解决三个问题

**背景**：开关/复选框的状态此前在 dump 里完全不可见（Switch 控件常无文本被过滤），导致
① 开关类动作只能用帧差猜验证；② 场景记忆"点击前后指纹相同"而反复命中同一动作（反复点开关）。

**改动**：
1. `dumpScreenCompact`：可勾选节点标 `v`（选中）/`o`（未选中）；过滤条件放宽
   （`|| node.isCheckable`——详情页的 Switch 常无文本，其标签在旁侧 TextView 上）
2. `dumpScreenJson`：节点加 `checkable`/`checked` 字段
3. `FastPicker.Candidate` 加 `checked`（true/false/null）
4. **`verify` 支持 `checkedText`**：文本节点与同行的可勾选节点做**空间关联**
   （y 中心差 < 80px），确认"该开关已选中"——比帧差可靠（帧差对开关动画会误报）
5. **`SceneMemory.fingerprint` 纳入勾选状态**（`v:`/`o:` 前缀）→ 开关开/关是不同指纹

**实测（2026-10-11）**：
- `verify={"checkedText":["启用深色主题"]}` → `verifyHow=['checkedText']` ✓（点击后状态确认）
- 记忆：第 1 次 stored → 第 2 次无计划 hit 执行成功 → **第 3 次（开关状态已变）不再命中**
  （指纹因 `v:`/`o:` 前缀不同）→ 正确地交回云端 ✓ —— **"反复点开关"的根因已修复**

### 8.2 判别头 v2（推演，未验证）

```
  本地闭环每步失败 ──► ESCALATE（带失败证据）──► 云端重新编译 + 给出"正确决策"
                                                          │
                                                          ▼
  本地训练池 += (目标, 屏幕候选快照, 正确决策)（脱敏：仅文本/结构，不上传截图）
                                                          │ 积累 N 条（如 200）
                                                          ▼
  云端离线蒸馏：bge 编码 + 决策头微调 ──► 新版本决策头（<1MB）──► 下发 → 本地热替换
                                                          │
                                                          ▼
              升级率下降（本地能处理的场景变多）──► 再次循环 ◄──
```

**可量化的成长指标**：升级率 = ESCALATE 步数 / 总步数。预期曲线：v1（纯余弦）→ v2（决策头）→ v3（积累后），升级率逐级下降，常用场景最终逼近全本地。这是赛道叙事里"越用越快"的硬证据，也是别人抄不走的（需要完整云端+本地+执行闭环才有日志数据）。

**隐私边界**：训练池只收集节点树文本与结构 + 目标描述，**不含截图与坐标轨迹**；上传前用户可查可清。

## 9. 落地步骤（Roadmap）

**阶段 A — 闭环跑起来**（先证明"本地连续执行"可行）
1. **闭环执行器骨架**（LocalLoopExecutor.kt）：决策程序 JSON 解析 + PICK→ACT→VERIFY 状态机 + RETRY/ESCALATE 策略——先用现有 FastPicker/Framer，云端暂不发程序，用测试用例喂 JSON
2. **云端编译侧**：AgentBridge 加 `/plan` 端点，大模型输出结构化决策程序（用现有云端多模态链路，输出格式约束为 DSL）
3. **实测对标**：模拟器跑"设置→关WiFi"全流程，统计每步耗时与升级率；再上 Canvas 场景（Framer 已有实测基础）

**阶段 B — 判别头升级**（前置条件：阶段 A 已产出真实升级日志且证明有必要）
4. **判别式回溯与 Score 层**：失败分流逻辑 + 双次匹配/多候选排序
5. **训练池**：ESCALATE 时落盘 (目标, 候选快照, 正确决策)，本地可查可清
6. **决策头 v2 训练管线**：云端用训练池微调判别头（bge 编码 + MLP 头），版本化下发

**阶段 C — 飞轮转起来**（前置条件：阶段 B 的决策头经实测确实优于纯余弦）
7. **自动蒸馏与热替换**：积累 N 条触发蒸馏，新决策头静默下发（灰度 + 回滚）
8. **成长看板**：升级率曲线 / 本地闭环覆盖率，作为赛道叙事的硬指标

> 说明：阶段 B/C 是方向，不是承诺。若阶段 A 的数据显示本地闭环本身效果不佳（比如升级率过高、每步耗时超预算），
> 应回头修阶段 A，而不是推进 B/C。

## 10. 阶段 A 实测数据（2026-10-10，模拟器 Android 16 / x86_64）

> 本轮实现并实测：`LocalLoopExecutor.kt`（决策程序 DSL 解析 + PICK→ACT→VERIFY 状态机
> + 判别式重试 + escalate 证据）、`/loop/run` 端点、`pressEnter()`（IME 回车）。

### 10.1 两个场景的结果

| 场景 | 步骤 | 闭环成功 | 独立核验 | 总耗时 | 单步 p50 |
|---|---|---|---|---|---|
| **设置里开启深色主题**（打开设置→显示和触控→深色主题→点开关→返回验证） | 5 | **6/6** | `ui_night_mode=2` 6/6 | **4.3s** | 932ms |
| **浏览器搜索+收集**（打开Chrome→回主页→点搜索框→输入网址→回车→点结果→收集存盘） | 7 | **5/5** | 收集文件含正文 5/5 | **6.7-7.5s**（首轮冷启 14.2s） | 972ms |

步级：场景 1 = 30/30 步成功；场景 2 = 35/35 步成功。**零 escalate**（两个场景的所有轮次）。

耗时构成（典型单步）：`actMs`（PICK+手势派发）3-60ms；`verifyMs`（等文本/帧差）270-950ms；
`settle`（等界面稳定）120-800ms。**慢在"等界面就绪"，不在判别本身**——这与设计预期一致
（本地判别 1-93ms，可靠性代价花在等待与验证上）。

### 10.2 实测踩过的坑（全部已修，按发现顺序）

1. **`settings put` 与 `cmd uimode` 不同**（测试方法坑，非代码 bug）：`settings put secure
   ui_night_mode 1` 只改数据库值，**不改 UiModeManager 内存状态** → 开关 UI 与系统值不同步 →
   点击"切换"净效果为零，表现为**成功/失败交替**的诡异模式。改用 `cmd uimode night no` 后 6/6。
2. **过渡期点击丢失**：页面跳转动画期间派发的点击会丢失（实测点击落在过渡页面上，开关没切换，
   但帧差因过渡动画误报"已变化"）→ 加 `settle()`：节点树签名连续 2 次一致（动态场景帧差兜底）。
3. **验证条件必须目标页独有**：s2 的 verify 曾用"深色主题"，而设置**首页**副标题
   "深色主题、字体大小、触控"也包含它 → 4ms 假通过、后续步骤全错位。改为"亮度"（显示页独有）。
4. **Chrome 工具栏按钮 desc 会变**：@759 位置在新标签页是"已退出账号。打开登录选项。"（账号按钮），
   在内容页才是"打开新的标签页" → 改用固定位置的"打开主页"（@63）作导航锚点。
5. **input 需带 target 自定位**：Chrome 主页渲染慢时前置点击的焦点会丢 → `inputText(text, append,
   targetText)` 先定位再写入（回退链：显式目标 > 当前焦点 > 首个可编辑节点），执行器 `input` 动作支持 target。
6. **ACTION_IME_ENTER 是 @hide**：`AccessibilityNodeInfo.ACTION_IME_ENTER` 编译不过，
   公开 API 是 `AccessibilityNodeInfo.AccessibilityAction.ACTION_IME_ENTER.id`（API 30+）。

## 11. 云端当场规划实测（2026-10-11）—— "云端编译 + 本地执行"完整链路

> 本节验证用户的核心命题：**不预先编码任何计划**，让云端大模型看当前屏幕**当场制定**
> 决策程序，本地闭环**当场判别执行**，失败则云端看新屏幕**当场改策略**。
> 实现：`scripts/probes/planner.py`（云端规划器，DeepSeek API）+ `agent_loop.py`（闭环驱动）。

### 11.1 任务与结果

**任务**：`通过浏览器找到软件安装包并下载打开查看`
（真实链路：Chrome → 资源站 → 找下载入口 → 点 APK 链接 → 处理"是否重新下载"确认框
→ 菜单→下载内容 → 点文件 → 系统安装确认界面 = 完成）

| 运行 | 轮数 | 结果 | 墙钟 | 云端合计 | 本地合计 | 本地步 |
|---|---|---|---|---|---|---|
| 1（调优后首跑） | 6 | ✅ | 26.2s | 6.3s（0.7-1.4s/次） | 15.4s | 7/8 |
| 2（稳定性验证） | 5 | ✅ | 53.3s | 5.7s | 44.2s | 2/5 |
| 3（稳定性验证） | 6 | ✅ | 25.8s | 6.1s | 15.4s | 6/7 |

**3/3 成功**，全部由云端当场判定"完成"（第 N 轮云端看到安装确认界面 → `done=true`）。

### 11.2 关键数据

- **云端规划 0.6-1.6s/次**（平均 ~1.1s，含判定+规划一次调用）——比"每步云端多模态 3-4s"快约 3 倍
- **本地执行占 70-89% 的时间**——瓶颈在本地等待（下载、界面渲染），不在云端
- **判别分布**：exact（FastPicker 精确匹配）为主，少数 none；本地判别本身 3-60ms
- **失败自愈实例**（运行 1）：第 3 轮点下载链接失败（弹"是否重新下载"）→ 第 4 轮云端
  看到确认框，**自己改变策略**："之前已下载过，应取消并走菜单→下载内容打开已下载文件"
  → 第 5 轮点文件 → 第 6 轮判定完成。**没有任何硬编码规则教它这个分支**。

### 11.3 Prompt 工程经验（都是实测踩出来的）

1. **"完成"的定义必须显式写进 prompt**：初版云端把"要更新此应用吗？"当障碍 → 点取消 →
   反复重开文件陷入循环。写明"看到安装确认界面 = 任务完成，直接 done=true"后解决。
2. **"等待"要教它用 `noop + verify.anyText`**：初版云端用 `sleep` 盲等（实测单步
   14.8s×3 次）。prompt 补充"等待某文本出现用 noop+verify，不要 sleep"后长等待消失。
3. **防重复规则**：初版云端反复点已下载过的链接 → "文件已存在/是否重新下载"死循环。
   写明"历史里已下载过就不要再点下载链接"后解决。
4. **给环境知识 ≠ 硬编码计划**：prompt 提供"测试站地址"和"Chrome 下载完成后的两条打开
   路径"（环境事实），站内有什么、怎么走由云端自己看屏幕决定——"寻找"的语义得以保留。

### 11.4 已知局限

- 本地执行耗时波动大（15.4s ↔ 44.2s）：等待类步骤（下载/渲染）不稳定，部分步 8.9-17.5s
- 云端偶尔给"不存在的锚点"（如"点击下载通知"）→ 本地 pick found nothing → 下一轮自我纠正
  （这恰好证明本地不做幻觉补偿、忠实失败并升级是安全的设计）
- 真实外网（Google 搜索页）路径可行但 DOM 不可控（云端点不中搜索结果链接），
  测试统一走本地资源站

## 11.6 判别头 baseline（2026-10-11 实测）—— 训练提升的对比基准

**为什么测**：此前只有端到端闭环成功率（6/6、5/5），**判别头本身的准确率从未系统测过**，
阈值 0.62 是拍脑袋定的。没有 baseline 就无法量化训练提升。

**测法**（`scripts/probes/eval_baseline.py`）：用 AndroidControl 判别集（test 2464 条抽样 300），
复刻 FastPicker.pick 的精确层 → 语义层 → 未命中逻辑，统计准确率/速度/分数分布。

**结果（跨语言最差情形：英文指令 + 中文特化 bge-small-zh）**：

| 指标 | Baseline | 训练后目标 |
|---|---|---|
| **Top-1 准确率** | **14.3%** | ≥60% |
| 精确层 | 命中 40%，**正确率仅 19%**（长句"包含"逻辑误命中严重） | — |
| 语义层 | 命中 42.7%，**正确率仅 16%** | — |
| 未命中（<0.62 交云端） | 17.3% | 降低 |
| **正确答案分数 p50** | **0.506**（低于阈值 → 被判"不知道"） | — |
| **错误候选分数 p50** | **0.673**（**反超正确答案** → 模型无区分力） | — |
| 精确层耗时 | ~0ms | — |
| 语义层耗时（21 候选/条） | **p50 331ms**（候选越多越慢） | <100ms（先粗筛再语义） |

**速度 baseline 补充**：单次嵌入调用 ~93ms（少量候选场景，test_embed.mjs 实测）；
候选 p50=20 时整条语义层 331ms——**候选数是速度关键变量**。

**两个已定位的具体缺陷（训练要解决）**：
1. **跨语言失效**：中文特化模型对英文 UI 文本无区分力（错误分数反超正确分数）
2. **精确层"包含"逻辑脆弱**：长句指令包含大量短候选文本 → 误命中（命中率 40% 但正确率 19%）

**中文场景 baseline（2026-10-11 补充，从闭环实测数据提取）**：

| 指标 | 中文场景（设置/浏览器，39 步成功） |
|---|---|
| **判别准确率** | **100%**（闭环成功 ⇒ 判别正确） |
| 精确层 | **39/39 = 100%** |
| 语义层 / 未命中 / 降级 | 0 / 0 / 0 |
| 判别分数 p50 | 1.000 |

**两个 baseline 并列的关键结论**：
- **中文场景判别不是瓶颈**：锚点是屏幕精确文本时，精确层 100% 命中，语义层一次未用、
  云端一次未升级 —— **训练的价值不在"提升当前场景"，而在"泛化"**：
  锚点不精确（"WLAN 开关" vs 屏幕"无线网络"）、文本变体、跨语言、新 App 陌生布局

## 11.7 判别头训练结果（2026-10-11）—— 14.3% → 50.9%

**训练**（`_dataset/train_head_frozen.py`，CPU）：
- 数据：AndroidControl 判别集，train 8000（抽样）/ val 2486（全量，episode 划分）
- 架构：MiniLM-L6-v2（22.7M，**冻结**）+ 交互特征 MLP（cos/diff/积/|diff| → 1153→256→64→1）
- 损失：listwise 交叉熵（同屏候选作 hard negative）
- 训练：200 epochs，嵌入预计算 + 去重（122476 文本 → 39556，减 68%），**约 8 分钟**（CPU）

**结果**：

| 指标 | baseline（bge-small-zh 精确+语义两层） | 新判别头 | 提升 |
|---|---|---|---|
| **val Top-1 准确率** | **14.3%** | **50.9%** | **+36.6pt（3.6 倍）** |
| 随机基线（12 候选） | 8.3% | — | 6.1 倍于随机 |
| 训练损失 | — | 1.789 → 0.155（ep1→ep180，val 在 ep40 后饱和 ~50.5%） | — |

**导出与部署体积**（`export_onnx.py`）：
- 编码器 int8 ONNX：**22.9MB**（fp32 版 90.9MB 权重外置；int8 权重内置）
- MLP 头 JSON：6.8MB（**可压到 1.3MB 二进制 / 0.3MB int8**——手机端手写 Kotlin 矩阵乘，无需 ONNX 运行时）
- **合计 ~24-30MB，远低于 100MB 上限** ✓

**推理速度**（PC CPU，ONNX int8 + numpy 头，端到端含编码+打分）：

| 候选数 | 耗时 p50 |
|---|---|
| 6 | **15ms** |
| 12 | 141ms |
| 20 | 250ms |

对比 baseline（bge 语义层 21 候选 331ms）：**全量候选略快（250 vs 331ms）**。
**关键**：配合粗筛（先用精确层 1-2ms，未命中再用关键词/字符相似度粗筛到 top-6）→
**判别头只需 15ms**，端到端比 baseline 快约 20 倍。这是推荐的上线架构：
**精确层 → 粗筛 top-6 → 判别头精选 → 仍无把握才升级云端**。

**待改进（诚实）**：
- 只训了 MLP 头（编码器冻结）+ 只用 8000/22495 样本 → 还有空间；微调编码器（需 GPU）
  与全量数据预计可到 60-70%
- val 在 ep40 后饱和（~50.5%）—— 冻结编码器的表达力上限
- 手机端速度待实测（预计 PC 的 1.5-3 倍；ONNX Runtime Android + Kotlin 头）

## 12. 视觉场景的决策扩展（纯图片/无文本界面）—— 设计

### 12.1 现状诊断（诚实）

| 层 | 纯图片场景下的状态 |
|---|---|
| PICK（FastPicker） | **完全失效** —— 输入是节点文本，没有文本就没有候选 |
| ACT（动作派发） | 可用（手势注入不依赖文本） |
| VERIFY（Framer） | **部分可用** —— 能判"画面变了没"，不能判"变对了没" |
| 云端规划 | **失效** —— dump 是空的，云端看不到屏幕内容 |

### 12.2 核心思路：扩展"感知源"，不动架构

决策的本质不变（Jev 心法：Choice 选一个 + Noul 没把握就升级），变的只是**候选从哪来**：

- 文本场景（现有）：候选 = 节点树文本
- 视觉场景（新增）：候选 = **OCR 文本** / **图标分类** / **视觉显著区域**

三种来源都归一化成"候选列表"，喂给**同一个** FastPicker 判别、**同一套**执行与验证层——
这正是分层的价值：加感知源不用重写执行/验证。

### 12.3 四层方案（按成本从低到高）

| 层 | 方案 | 覆盖场景 | 耗时 | 成本 |
|---|---|---|---|---|
| **V1** | **OCR 桥接**：本地离线 OCR（MLKit Text Recognition 或 PaddleOCR mobile），把画面文字提取成"文本+坐标" | "图里有字但节点树没有"——WebView/Canvas/游戏 UI **大量带字** | ~100-300ms | 低（集成 SDK，零训练） |
| **V2** | **图标符号库**：常见 UI 符号有限枚举（返回/关闭/菜单/设置/播放/加号/搜索…约 50-200 个），模板匹配（感知哈希/特征点）或极小分类器 | "简略符号"类——用户说的无字图标 | 10-50ms | 中（需采集/标注样本，可增量积累） |
| **V3** | **显著区域检测**：纯算法找"像按钮"的区域（色块/边缘/对称性/尺寸启发） | 真·纯图形兜底（不知道是什么，但知道"这里像能点"） | <20ms | 低（零训练） |
| **V4** | **云端一次性理解**：多模态看一帧 → 给出目标坐标/区域 → 本地执行 + Framer 验证 + 结果缓存复用 | V1-V3 全失败 | 3-5s/次（只在关键节点，不是每步） | 低（现有 API） |

**关键判断**：真正的"一点文本都没有"的场景比想象的少——大部分"图片型界面"（网页、
小程序、多数游戏 UI）其实**有字**，只是节点树里没有。所以 **V1（OCR 桥接）能覆盖大头**，
V2 处理真符号，V3/V4 兜底。

### 12.4 Framer 的角色升级（视觉场景的守卫）

视觉场景里 Framer 从"验证器"升级为"守卫"：
- **点击前**：记录目标区域的局部指纹（不是全屏帧）
- **点击后**：变化必须发生在**预期区域**（现在只判全屏"变了没"，会漏"点错地方也有变化"）
- **复用前**：同一操作回放/复用前校验局部指纹，画面变了就升级云端重新理解

### 12.5 优先级建议

1. **V1 OCR 桥接先行** —— 把 80% 的"伪纯图片"场景拉回现有链路，成本最低收益最大
2. **V4 云端理解做"关键节点的一次性投资"** —— 一次理解、多次本地复用（配合 12.4 的指纹守卫）
3. **V2 图标库按实际遇到的符号增量收集** —— 不必一次枚举完，先用 V3/V4 顶着

### 12.6 合规边界

OCR / 图标识别 / 视觉区域检测是通用无障碍能力（自己的应用、自动化测试、辅助操作均属正常）。
游戏场景按用途区分：自己游戏的辅助操作可做；打金/多开/反作弊绕过不做
（见 COMPLEX_SCENARIOS.md「合规红线」）。

## 13. 通用视觉下的自由操作：能力边界与可行路径

> 问题：云端多模态 + 本地决策，能否在**任意视觉场景**（不限文本界面、不限方块游戏）下自由操作？

### 13.1 先把"自由操作"拆开——两类问题的难度天差地别

| 类别 | 内容 | 可行性 | 原因 |
|---|---|---|---|
| **操作类** | 找目标、移动过去、点击/采集、开关、放置 | ✅ **可行** | 目标可视觉追踪 + 动作可视觉验证，是闭环问题 |
| **策略类** | 战斗、解谜、语义推理（"找那个 NPC 对话"）、连招 | ❌ **不可行** | 这是通用游戏 AI / VLA 问题，前沿研究未解决，手机端更不可能 |

"通用视觉自由操作"没有银弹——通用视觉-语言-动作模型（VLA，如 RT-2/OpenVLA 类）
是当前 AI 最前沿方向，**没有任何一个能在手机上实时跑**。但**操作类任务不需要 VLA**。

### 13.2 可行架构：云端"慢思考" + 本地"快反射"

**关键认知：云端多模态不是每步都用，而是"一次性理解 + 编译"。**

```
进入新场景/卡住时（云端，3-5s，一次）：
  看一帧 → 场景理解（这是什么、有哪些可操作目标）
        → 编译成「视觉行为程序」：目标视觉特征 + 行为序列 + 判别条件

运行中（本地，毫秒级，每帧）：
  ① 视觉伺服：在画面里追踪目标（模板匹配/颜色特征）→ 目标在哪个方向 → 转向/移动
  ② 状态判别：目标区域的变化（变大了=接近了、消失了=采集了）→ 推进状态机
  ③ 动作执行：连续控制（长按拖动=摇杆）+ 离散动作（点击/长按）
```

**为什么核心是"视觉伺服"而不是"理解每一帧"**：
- "理解每一帧"= VLA 的活 → 手机跑不动
- "追踪一个视觉目标"= 机器人领域成熟技术（visual servoing）→ 毫秒级、本地可做
- 泛化性来自：**目标模板由云端一次性给出**（"那棵树长这样"），本地只负责追踪

### 13.3 视觉行为程序（我们架构的延伸形态）

云端编译产物从"节点锚点"扩展为"视觉特征 + 行为序列"：

```json
{
  "goal": "砍一棵树",
  "target_spec": {"visual": {"color_hist": [0.4,0.3,0.2], "texture": "vertical", "shape": "column"}},
  "behaviors": [
    {"state": "SEARCH",   "action": "turn",         "until": "target_found",     "verify": "template_match"},
    {"state": "AIM",      "action": "servo_center", "until": "target_at_center", "verify": "center_match"},
    {"state": "APPROACH", "action": "forward",      "until": "target_ratio>0.3", "verify": "area_growth"},
    {"state": "ACT",      "action": "long_press",   "until": "state_changed",    "verify": "region_diff"}
  ]
}
```

**这正是我们"云端编译 + 本地执行"架构的通用形态**：编译层把云端理解转成本地可判别的规则，
本地每帧只做判别与控制——**不"理解"，只"跟踪"**。这是通用 VLA（太大）与纯本地视觉
（太笨）之间的**唯一可行中间路线**。

### 13.4 泛化边界（诚实）

| 场景 | 可行性 | 说明 |
|---|---|---|
| 目标视觉特征明显（树/宝箱/敌人/道具/按钮图标） | ✅ | 模板/颜色可追踪 |
| 目标需语义识别（特定 NPC、任务物品、同类中挑一个） | ⚠️ | 云端一次辅助可解（看一帧指定目标） |
| 动作效果可视觉验证（走近、采集、开关） | ✅ | 区域变化判别 |
| 需要策略（战斗走位、解谜、社交） | ❌ | 超出范围 |
| 高频反应（闪避、连招、瞄准） | ⚠️ | 简单反射可做（固定规则），复杂反应不行 |

### 13.5 与现有架构的关系

- **执行层复用**：无障碍手势（长按拖动=虚拟摇杆、点击、滑动）已验证可用
- **验证层升级**：Framer 从"全屏变了没"升级为"**局部区域指纹**"（目标区域变化才作数）
- **决策层换源**：候选从"节点文本"换成"视觉特征/模板位置"（第 12 节的分层同理）
- **云端角色明确**：慢思考（理解+编译），不参与实时循环

### 13.6 视觉伺服验证结果（2026-10-11 实测，PC + OpenCV + 真实方块游戏截图）

**验证设置**：Minetest 截图（1018×600，草地/树/天空，准星居中），降采样到 160×94 处理
（手机端同款思路）；云端给的目标 = 中央树树冠区域（100×100）→ 降为 15×15 模板。

**✅ 位置追踪（视觉伺服的核心）：可行**

| 指标 | 结果 |
|---|---|
| 匹配位置误差 | **1px**（期望 83,52 → 实测 84,52） |
| 置信度 | 0.880 |
| 耗时 | **p50 0.39ms**（PC/cv2；手机端手写 NCC 预估 5-15ms） |
| 视角平移追踪（9 帧） | 轨迹 **104→100→94→90→84→80→74→70→64 完美单调**（视角右移→目标左移）✓ |
| 同类干扰 | 本场景仅 1 个高分峰（树叶纹理各异）；低区分度模板需时间连续性约束 |

**❌ 距离/尺度估计：四种方法全部失败（诚实记录）**

| 方法 | 结果 | 失败原因 |
|---|---|---|
| 多尺度模板匹配 | 近景反而匹配到更小尺度 | **方块纹理是高频细节，缩放后失真**，NCC 分数不可比 |
| 颜色反向投影（CamShift 思路） | 目标色占屏 0.0-0.1%，无区分度 | **树叶与草地都是绿**，颜色区分不足 |
| 高分匹配点散布 | 中/近景无高分点 | 同缩放失真 |
| 纹理能量占比（局部方差） | **方向反了**（近景 1.0% < 远景 18.0%） | 放大后降采样把方块纹理**抹平**，高频能量反而下降 |

**根本教训**：方块游戏（及一切高频纹理场景）中，**任何依赖纹理的尺度/距离估计都不可靠**；
纹理只能用于**同尺度下的位置匹配**。

**✅ 替代方案：用"到达判据"取代"距离估计"**（不需要知道还有多远，只需知道到了没有）

| 子问题 | 方案 | 依据 |
|---|---|---|
| 目标在哪个方向 | 模板匹配（NCC）→ 位置 → 转向量 | 已验证，0.39ms |
| 对准了吗 | **中心区域匹配分数** > 阈值 | 模板匹配的副产品，零额外成本 |
| 到了吗（前进判据） | **固定时长步进 + 帧差**：画面还在变=还在走；画面不动=撞到障碍 | Framer 已有能力（第一人称撞墙/撞树时画面确实静止） |
| 交互成功了吗 | **固定 UI 区域变化**（物品栏格子） | 帧差的局部区域版 |

**结论**：**操作类任务（找目标→转向对准→靠近→交互）全线可行**，且全部组件都在现有能力范围内
（模板匹配新增 ~100 行 Kotlin，帧差/局部帧差复用 Framer，控制复用无障碍手势）。
唯一被否掉的是"精确距离估计"——但它不是必需的。

### 13.7 手机端视觉定位实测（2026-10-11，模拟器 Android 16）

**验证目标**：无节点树场景的"视觉定位 → 点击 → 状态确认"闭环
（对应手机游戏的真实操作模型：**虚拟按钮点按 + 摇杆/视角拖动**，全是手势层能力，
缺的只是"按钮在哪"）。

**实现**：`VisionTracker.kt`（本地 NCC 模板匹配）+ 端点组
`/vision/crop`（云端圈目标 → 存模板）→ `/vision/track`（定位）→ `/vision/tap`（定位+点）
/ `/vision/drag`（定位+拖，摇杆用）。

**测试场**：`testsite/game.html`（Canvas 渲染：中央目标方块 + 右下攻击按钮 + 左下摇杆
+ 动态血条，**无任何文本节点**——FastPicker 完全失效，纯视觉场景）。

**结果（3/3 一致）**：

| 指标 | 数据 |
|---|---|
| **定位精度** | **2px**（866,2051 vs 期望 865,2049） |
| **定位耗时** | **89-183ms（p50 ~100ms）** |
| 模板 | 235×234 原图 → 31×31（处理分辨率） |
| 处理分辨率 | 长边 320（帧 144×320） |
| 搜索区域 | 右下 1/4（**云端先验**：看懂画面时就知道目标在哪，限制区域既提速又防误匹配） |
| **端到端** | 定位+点击 → **游戏状态变化确认（score 0→10，目标方块消失）** ✓ |

**五个实测坑（都已修，按踩坑顺序）**：
1. **模板按自身长边降采样** → 得到比处理帧还大的模板 → 匹配直接失败（必须按帧的同一比例缩放）
2. **灰度匹配特征不足**：红圆环按钮 vs 红血条在灰度下几乎一样 → 改 **RGB 三通道 NCC**
3. **处理分辨率 160 太低**：模板仅 13×13，全屏搜索误匹配（分数虚高 0.99、位置全错）→ 提到 320
4. **裁到纯色背景**：模板无特征 → 随机匹配任意区域且分数虚高 → crop 加**平坦检测**（灰度方差 < 120 拒绝）
5. **连续截图偶发超时** → track 加重试 3 次

**遗留**：`screenshotArgb` 连续调用偶发失败（帧差端点 `/frame-diff` 也受同一影响）——
需统一加重试（下一步）。

**对"通用视觉操作"的意义**：这条链路证明了**用户判断的正确性**——手机游戏操作无非
"点按钮 + 拖摇杆/视角"，都是无障碍手势能做的；本地要补的只是**视觉定位**（已跑通，100ms、
2px）。云端负责"看懂画面、圈出目标、给出区域先验"，本地负责"毫秒级定位 + 手势执行"，
分工闭环成立。

### 13.8 反应速度升级路径（低延迟决策，2026-10-11 实测基准）

**问题**：当前串行链路（截图→匹配→手势）实测 250-400ms，**慢于人类反应**（150-250ms，
职业玩家 100-150ms）。瓶颈已定位、可优化。

**实测基准**（模拟器 Android 16）：

| 环节 | 当前实测 | 说明 |
|---|---|---|
| **截图** | **p50 336ms**（min 64 / max 513） | **最大瓶颈**，且波动大——每次 `takeScreenshot` 是完整 IPC + 编码 |
| 匹配（全屏） | 883ms | Kotlin 手写 NCC 全屏搜索 |
| 匹配（区域 1/4） | 170ms | 区域限制已验证有效 |
| **匹配（区域 ~2%）** | **10-39ms（p50 12ms）** | **增量追踪的可行性证据**——目标在上一帧附近时搜索区域可缩到极小；对比全屏 774ms，**约 64 倍加速** |

**实测补充（2026-10-11 二轮）**：
- 搜索区域与耗时关系（同一目标，3 次取 p50）：小区域(按钮附近) **12ms** / 右下 1/4 **128ms** /
  全屏 **774ms** —— 区域限制是延迟优化的关键杠杆。
- 本轮修掉的 4 个真 bug：① `screenshotArgb` 默认超时 1500ms 太短（模拟器上 ARGB 全屏
  拷贝超过它 → 静默返回 null），改 5000ms；② 截图调用走 `screenExec` 单线程池会被节点树
  IPC 挂起拖死（`/screenshot` 端点因直连而不受影响），track/crop 改直连；③ 搜索区域比
  模板还小时静默失败（返回 match failed），改为自动扩展到"装得下模板 + 余量"；
  ④ `/vision/track` 响应 `"id"` 缺引号（非法 JSON，调用方解析失败）。
- 待查：极小区域（37×37）下偶发未命中（score=-2.0，所有窗口被判无效）——不影响
  "区域限制大幅提速"的结论，下一步排查。

**四个升级点**（按收益排序）：

1. **MediaProjection 帧流**（最大提速，截图 336ms → **<5ms**）
   不再每次调 `takeScreenshot`（完整 IPC + 编码），改用持续录屏流：屏幕内容实时推送到
   App 内存，取帧是内存拷贝。需要用户授权一次（录屏权限）。这是游戏/录屏类 App 的标准做法。
2. **增量追踪**（匹配 883ms → **<5ms**）
   目标在上一帧位置附近（±10%）→ 搜索区域缩 25 倍（实测 17ms）→ 再叠加金字塔/NEON 优化
   到个位数毫秒；只在目标丢失时全屏重捕（883ms，偶发）。对应经典追踪器架构
   （MOSSE/KCF 的思路：帧间增量 + 丢失重捕）。
3. **流水线并行**（总延迟从 sum 变 max）
   截图线程（持续抓帧）→ 匹配线程（处理最新帧）→ 手势线程（派发），三线程流水线重叠：
   匹配第 N 帧时截图已在抓第 N+1 帧。有效延迟 ≈ max(各环节) 而非 sum。
4. **运动预测 + 提前派发**（补偿残余延迟）
   由目标前几帧位置/速度做线性预测（或卡尔曼滤波）→ 在目标**到达预测位置前**派发手势，
   把"看到才反应"变成"预判落点"——这是人脑在对抗中反应快的真正秘诀（预测而非纯反应）。

**升级后预期**：帧流 5ms + 增量匹配 5ms + 手势 50ms ≈ **60ms**（再叠加预测补偿可更低），
**反超人类反应速度**。

**合规边界（明确，不随技术升级改变）**：
- 这套低延迟视觉能力是**通用能力**：单人游戏、自己的服务器、自动化测试、辅助操作均属正常。
- **PVP 竞技对抗不做**：实时对抗中自动操作破坏公平、违反游戏 ToS、会触发反作弊——
  与"游戏脚本/打金"同属红线（见 COMPLEX_SCENARIOS.md）。技术方案提供，但用途边界不放宽。

## 14. 明确不做的事
- ❌ 不引入任何新模型（Laya/Kev/Jev 均排除：体积 803MB-1.6GB，PyTorch 栈，手机不可行）
- ❌ 不做通用决策（Jev 的合同/客服/路由场景与我们无关——赛道差异就在"UI 特化"）
- ❌ 本地不做生成式理解（0.8B 自回归在手机上 200-500ms 且需要 ~700MB 内存，性价比不如云端编译）
- ❌ 训练池不收截图与坐标轨迹（隐私边界，见第 8 章）
- ❌ 不碰合规红线（游戏自动化、反作弊绕过等，见 COMPLEX_SCENARIOS.md「合规红线」）
